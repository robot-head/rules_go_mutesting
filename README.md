# rules_go_mutesting

A Bazel aspect that runs Go mutation testing over any
[rules_go](https://github.com/bazel-contrib/rules_go) target, using
[go-mutesting](https://github.com/jonbaldie/go-mutesting). Every option the
tool supports is exposed as a Bazel build setting, and mutation testing can be
restricted to the lines changed since a git ref.

Mutation testing measures how good your tests are: it makes small changes to
your code (mutants) and checks whether any test notices. A mutant that no test
catches has *escaped*, and points at a gap in your test suite.

## Setup

```starlark
bazel_dep(name = "rules_go_mutesting", version = "0.1.0")
```

The mutation engine comes with the module, so there is nothing else to declare.
go-mutesting v2.8.2 needs a Go 1.26 or newer SDK.

## Running it

Mutate one target:

```bash
bazel build //path/to:my_test \
  --aspects=@rules_go_mutesting//mutesting:aspect.bzl%go_mutesting_aspect \
  --output_groups=mutesting_report
```

That is a mouthful, so put it in your `.bazelrc` once:

```
build:mutesting --aspects=@rules_go_mutesting//mutesting:aspect.bzl%go_mutesting_aspect
build:mutesting --output_groups=+mutesting_report
```

and then sweep the whole repository:

```bash
bazel build //... --config=mutesting
```

Each target gets `<name>.mutesting.report.json` and `<name>.mutesting.log` in
its output directory. Non-Go targets are ignored, so a repository-wide pattern
is safe.

**Point it at `go_test` targets.** Mutants are killed by tests, so running the
aspect on a bare `go_library` reports every mutant as escaped. A sweep over
`//...` covers both, and the library results are only meaningful as a list of
what *could* be tested.

## Failing a build on a low score

```bash
bazel build //... --config=mutesting \
  --@rules_go_mutesting//mutesting:min_msi=70
```

The action fails when the mutation score falls below the threshold. Because
Bazel discards the outputs of a failing action, the score and the escaped
mutants are also written to stderr.

For per-target thresholds that run under `bazel test`, use the rule:

```starlark
load("@rules_go_mutesting//mutesting:defs.bzl", "go_mutesting_test")

go_mutesting_test(
    name = "adder_mutation_test",
    target = "//examples/adder:adder_test",
    min_msi = "50",
)
```

## Only the lines you changed

A full mutation run is expensive. To measure only what a change touches:

```bash
bazel run @rules_go_mutesting//mutesting:changed -- --base origin/main
```

This compares the merge base of `origin/main` and your working tree, so
uncommitted edits count. There is no default base ref; you always name one.

It finds the changed Go files, maps them to the `go_test` targets that own
them, and mutates only the lines in the diff. Output looks like:

```
mutesting: 1 changed Go file(s) since c92b49a295ba, 1 target(s) to mutate:
  //examples/adder:adder_test
...
Changed-lines mode: 2 of 11 mutations fall on changed lines.
The mutation score is 100.00% (2 killed, 0 escaped, ...)
```

Options: `--scope` narrows the target search (default `//...`), `--dry-run`
shows what would run, and anything after a bare `--` is passed to the
underlying `bazel build`:

```bash
bazel run @rules_go_mutesting//mutesting:changed -- --base origin/main \
  -- --@rules_go_mutesting//mutesting:workers=4
```

How it decides what to run:

- Only packages whose own sources changed are mutated. A change to a dependency
  does not re-run its dependents, because it does not change their mutants.
- A package with no `go_test` target is skipped with a warning; its mutants
  could not be killed by anything.
- A change to only `_test.go` files produces an empty report rather than a
  failure. Changed-lines mode answers "are my new lines tested", not "do my new
  tests kill old mutants".
- Files generated by the build never appear in a git diff, so they are not
  mutated in this mode.
- A target with no mutations in scope reports zero mutants and passes. It is
  not treated as a threshold failure.

In CI, make sure the base ref exists: a shallow clone needs
`fetch-depth: 0` or an explicit `git fetch` before the run.

## Options

Every option is a build setting under `@rules_go_mutesting//mutesting:`. Set
any of them on the command line:

```bash
bazel build //... --config=mutesting \
  --@rules_go_mutesting//mutesting:disable=arithmetic/* \
  --@rules_go_mutesting//mutesting:workers=8
```

List settings take one value per repetition
(`--@...//mutesting:disable=a --@...//mutesting:disable=b`).

### Selecting what to mutate

| Setting | Type | Description |
|---|---|---|
| `disable` | list | Mutators to turn off, by name or `prefix/*`. |
| `enable` | list | Allowlist of mutators; `disable` still applies on top. |
| `match` | string | Only mutate functions matching this regex. |
| `only_files` | list | Workspace-relative `.go` files to mutate. |
| `exclude_dirs` | list | Path prefixes to leave alone. |
| `ignore_source_lines` | list | Regexes; matching source lines are not mutated. |
| `skip_without_test` | bool | Skip files with no sibling `_test.go`. |
| `skip_with_build_tags` | bool | Skip files whose test file carries build tags. |
| `exclude_mutants` | label | File of mutation checksums to skip, one per line. |
| `changed_lines_spec` | string | Set by the `:changed` runner; not for hand use. |

Run `bazel run @rules_go_mutesting//mutesting:tool -- --list-mutators` to see
all 33 mutators.

### Running the tests

| Setting | Type | Default | Description |
|---|---|---|---|
| `workers` | int | 0 | Parallel workers; 0 means one per CPU. |
| `exec_timeout` | int | 10 | Seconds allowed per mutant. |
| `timeout_coefficient` | string | | Timeout as a multiple of the baseline test run; overrides `exec_timeout`. |
| `test_flags` | string | | Extra flags for each `go test` run. |
| `coverage` | bool | false | Compute covered-code score. |
| `per_test` | bool | false | Run only the tests that cover each mutant. |
| `noop` | bool | false | Run the suite once unmutated first and fail if it does not pass. |
| `test_recursive` | bool | false | Include subpackages. |
| `exec_script` | label | | Executable to run per mutant instead of the built-in runner. |
| `no_exec` | bool | false | Generate mutants without running tests. |
| `dry_run` | bool | false | Count mutations without generating or running them. |

An `exec_script` receives `MUTATE_CHANGED`, `MUTATE_ORIGINAL`,
`MUTATE_PACKAGE`, `MUTATE_TIMEOUT`, `MUTATE_DEBUG` and `MUTATE_VERBOSE`, and
must exit 0 for killed, 1 for escaped, 2 for skipped. Setting it forces
`workers` to 1 and disables `test_flags`.

### Scoring

| Setting | Type | Description |
|---|---|---|
| `min_msi` | string | Minimum mutation score, 0-100. Empty means no gate. |
| `min_covered_msi` | string | Minimum covered-code score; needs `coverage`. |
| `fail_on_escaped` | bool | Fail if any mutant escapes. |
| `ignore_msi_with_no_mutations` | bool | Pass the gate when nothing was mutated. |
| `baseline` | label | Baseline file of already-escaping mutants to tolerate. |

Write a baseline with:

```bash
bazel run @rules_go_mutesting//mutesting:update_baseline -- ./path/to/pkg
```

Note that the score counts mutants that errored or failed to compile as
killed.

### Reports and output

| Setting | Type | Description |
|---|---|---|
| `html_output` | bool | Also write an HTML report. |
| `logger_summary_json` | bool | Also write a stats-only JSON report. |
| `logger_agentic_json` | bool | Also write the LLM-oriented escaped-mutant JSON. |
| `logger_gitlab` | bool | Also write a GitLab Code Quality report. |
| `logger_github` | bool | Emit GitHub Actions warning annotations. |
| `quiet`, `verbose`, `debug`, `no_diffs`, `output_statuses` | | Control log detail. |

Each enabled report becomes an extra file in the `mutesting_report` output
group. `report.json` is always produced.

### Escape hatches

| Setting | Type | Description |
|---|---|---|
| `config` | label | A go-mutesting YAML config used as the base; settings are layered on top. |
| `extra_args` | list | Arguments appended verbatim to the tool invocation. |
| `keep_tmp` | bool | Keep the staged module and generated mutants for debugging. |

## How it works

The aspect reads the rules_go providers for a target and stages a
self-contained Go module in the action's temporary directory: the package under
test at the module root, and every transitive dependency either nested under
the module path or vendored with a generated `go.mod` and `vendor/modules.txt`.
The engine then runs against that module with `GOPROXY=off`, so the whole run is
offline and cacheable. Results are cached per target and only recomputed when
sources or options change.

Changed-lines mode works in two passes inside the same action. The first
generates every mutation without running any tests, which is an AST-level pass.
The runner then computes each mutation's checksum, keeps those that fall on
changed lines, and passes the rest to the engine's exclusion list for the second
pass, which actually runs the tests. go-mutesting's own `--git-diff-lines`
option is exposed as `git_diff_lines` but cannot work inside a sandbox, since
there is no git repository there; the `:changed` runner is the supported route.

## Limitations

- **cgo is not supported.** Targets that need cgo report a skip instead of a
  score, so that repository-wide sweeps stay green.
- The engine shells out to `diff`, which is expected on the host `PATH`. This
  is the one part of the action that is not hermetic.
- Each action compiles the standard library into its own scratch cache the
  first time it runs, which adds some seconds per target.
- `--git-diff-lines` and `--git-diff-base` are exposed for completeness but do
  not work in a sandboxed action.

## Development

```bash
bazel test //...                       # unit tests and the example gates
bazel build //... --config=mutesting   # mutation-test this repository
bazel run //mutesting:tool -- --list-mutators
```

The `examples/` packages are deliberately uneven: `adder` has weak tests so
that mutants escape, and `calc` has thorough ones.

`e2e/bcr_test/` is a separate module that consumes this one the way a real
user would. It is what the Bazel Central Registry runs as a presubmit, so run
it before releasing:

```bash
cd e2e/bcr_test && bazel test //... --override_module=rules_go_mutesting=../..
```

## Releasing

The module is set up for the
[Publish to BCR](https://github.com/bazel-contrib/publish-to-bcr) app, which
opens the registry pull request from a GitHub release. Install the app on this
repository once; the placeholders in `.bcr/` (`{OWNER}`, `{REPO}`,
`{VERSION}`, `{TAG}`) are substituted automatically.

Then, for each release, set `version` in `MODULE.bazel` to match and publish a
GitHub release whose tag is that version:

```bash
git tag v0.1.0 && git push origin v0.1.0
gh release create v0.1.0 --generate-notes
```

The release workflow attaches a reproducible source archive, and the app
computes its integrity hash and opens the pull request against
[bazel-central-registry](https://github.com/bazelbuild/bazel-central-registry).

The archive has to be a release asset rather than the tag tarball GitHub
generates on demand: the registry rejects the latter, whose checksum is not
guaranteed to stay stable. That is why the workflow builds one with `gzip -n`
and `.bcr/source.template.json` points at
`releases/download/{TAG}/{REPO}-{VERSION}.tar.gz`.

To submit manually instead, add
`modules/rules_go_mutesting/<version>/{MODULE.bazel,source.json}` and update
`metadata.json` in a fork of the registry, filling in `source.json` with the
release archive URL, its `strip_prefix`, and its SRI integrity hash.
